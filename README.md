# LLM SQL Guard

Day 1 mini project: a text-to-SQL pipeline (Claude API) against a synthetic
UK banking database, with a `sqlglot`-based structural guard that inspects
generated SQL before deciding whether to execute it.

## Pipeline

```
question (natural language)
    -> app/llm_client.py   Claude generates a SQL SELECT
    -> app/sql_guard.py    sqlglot parses the SQL and flags:
                              - more than one statement (stacked-query injection)
                              - non-SELECT statement types
                              - UNION (data exfiltration)
                              - tautologies in WHERE (e.g. 'a'='a')
                              - references to tables outside the schema
    -> app/main.py /ask    logs the attempt, then either blocks or executes
                            depending on `enforce_guard`
```

`enforce_guard=false` (default) executes the generated SQL regardless of the
guard's findings — this is what an undefended text-to-SQL pipeline does, and
is the mode to use when demonstrating an injection. `enforce_guard=true`
blocks execution whenever the guard finds an issue — this is the mitigation.

## Setup

```bash
source .venv/bin/activate   # or create one: python -m venv .venv
pip install -r requirements.txt
cp .env.example .env        # then put your real ANTHROPIC_API_KEY in .env
python -m app.db            # initialise + seed banking.db
uvicorn app.main:app --reload --port 8000
```

Open http://localhost:8000.

## Files

- `app/db.py` — schema + synthetic UK banking data (customers, accounts, transactions) + audit_logs table
- `app/llm_client.py` — calls Claude to turn a question into a SQL SELECT
- `app/sql_guard.py` — sqlglot-based structural analysis of generated SQL
- `app/main.py` — FastAPI app, `POST /ask`, static frontend

## Notes

- `.env` holds the real `ANTHROPIC_API_KEY` and is gitignored; `.env.example` is the template.
- `banking.db` is gitignored and regenerated by `python -m app.db`.
- The guard is deliberately a first cut: it validates structure, not values (e.g. it won't catch a query that legitimately parses as SELECT but leaks more rows than intended via a broad LIKE). That's a good next iteration.
